## 2. Library Evaluation

Detailed trade-offs for each choice. Verdict rows are what `scale-100M` will adopt.

### 2.1 ANN index (IVF-PQ / DiskANN / scalable HNSW)

| Candidate | Lang | LoC order | Pros | Cons | Verdict |
|---|---|---:|---|---|---|
| **usearch** (rust-bindgen) | C++ w/ Rust bindings | ~8k C++ | production-grade, HNSW + i8/bf16 quant, bindings stable, MIT | C++ dep, no native IVF-PQ | **ADOPT for PR-A1** as drop-in upgrade for HNSW path |
| `hnsw_rs` | pure Rust | ~3k | no C++, good quality | HNSW-only, memory-heavy at 100M | keep as fallback |
| `instant-distance` | pure Rust | ~1.5k | zero-cost, mmap support | no quant, slower build | NO |
| **faer** + hand-rolled IVF-PQ | pure Rust + SIMD | +2-3k our code | full control, SIMD native | 2-3 weeks of careful work | **ADOPT for PR-A2** as Synapse-native IVF-PQ on top of faer kmeans + int8 residuals |
| `qdrant-core` crate | Rust | 50k+ | mature IVF/HNSW | not published as reusable lib | NO |
| DiskANN Rust port | — | 5k+ | SSD-optimised, 100M native | no vetted Rust port in 2026 | later (P2) |

**Decision**: ship `synapse-ann` crate with two backends — `usearch` (fast time-to-market) and `synapse-ivfpq` (Rust-native, becomes primary). Selector feature-flag.

### 2.2 Storage / segment layer

| Candidate | Lang | Pros | Cons | Verdict |
|---|---|---|---|---|
| **redb** | pure Rust | already a dep, zero-copy mmap, ACID, simple | single-writer, no LSM compaction | **KEEP** for cache + metadata |
| **fjall** | pure Rust | LSM-native, partitioned keyspaces, tombstones, compaction | new (2025), less battle-tested | **ADOPT for PR-B1** as segment store |
| `sled` | pure Rust | LSM+Bw-tree | project health uncertain (fork churn) | NO |
| RocksDB | C++ | industry default | C++ toolchain, binary size, build time | NO (kept off for single-binary promise) |
| `slatedb` | pure Rust | on S3 by default | S3-centric; single-file goal bleeds | later, optional |

**Decision**: `fjall` for vector/segment LSM; `redb` stays for the embedding cache; SQLite stays for FTS5 + metadata. Single-file `.synx` distribution = zstd-wrapped concat of these (header says which).

### 2.3 Quantization

| Candidate | Integration | Compression | Recall loss |
|---|---|---:|---|
| **int8 (linear scale per dim)** | 10-row helper in synapse-quant | **4×** | typ. < 1 % |
| **Matryoshka truncation 384→256 + int8** | swap embedder model | **12×** | 1-2 % when trained-for |
| **PQ (product quantization)** | inside synapse-ivfpq | **32-64×** | 3-6 % without rerank |
| RaBitQ 1-bit | research | **128×** | needs rerank |
| **Candle vs Burn vs MLX** (for quant math) | | | Candle = ndarray-like, stable, pure Rust; MLX = Metal-only but 3-5× faster quant. Verdict: **Candle default, MLX opt-in (`features=mlx`)**. |

**Decision**: int8 immediately, PQ inside ivfpq, Matryoshka as `features=matryoshka` once embedder swap lands.

### 2.4 WAL / durability

| Candidate | Notes | Verdict |
|---|---|---|
| SQLite WAL mode | already there for metadata | **leverage** |
| fjall write-ahead | LSM-native | **leverage** |
| hand-rolled append-only log | for vector segments | write `synapse-wal` crate, ~400 LoC |

**Decision**: compose WAL from SQLite+fjall+synapse-wal. No custom fsync primitives.

### 2.5 Concurrency API

Target: `Arc<Db>` with `fn query(&self, ...) -> Result<...>` callable from N threads without locking the read path.

- Lock-free HNSW search: supported by `usearch` (concurrent search, serialized write).
- IVF-PQ search: trivially parallel per-list; **ADOPT**.
- Background compaction: `tokio::spawn` OR dedicated `std::thread` pool; **choose std::thread to avoid forcing tokio on lib users**.

## 5. Scale-100M Reality Arithmetic (defense, not fabrication)

At 100M × 384d × float32 = **153.6 GB** raw vectors. Not fittable in 128 GB RAM. Required reductions:

| Change | Factor | Result @ 100M |
|---|---:|---:|
| float32 → int8 quant | 4× | 38.4 GB |
| + Matryoshka 384→256 | × 1.5 | 25.6 GB |
| + IVF-PQ m=32 subspaces (8-bit each) | ~32× over int8 | **1.2 GB centroids + 3.2 GB codes** |

**Post-PR-A2+C1+C2, Synapse @ 100M should fit in <5 GB index RAM + 30 GB disk for payloads/FTS/KG.**  This is the arithmetic that justifies the plan. **Not a measured number.** It will become measurable after PR-A2 ships.

## 8. What This Plan Will NOT Attempt

- Beating Milvus on enterprise multi-tenant features. Different product.
- Managed-cloud offering. Synapse stays a lib/binary.
- Replacing Qdrant at 1B+ scale. Target is 1M-100M single-node.
- Benchmark numbers at 100M measured on this M4 Max. 100M requires either int8/PQ (= post-PR-A2) or a bigger machine. Plan commits to measuring at 10M on this hardware; 100M with projection + caveat marking until a ≥256 GB node is available.
